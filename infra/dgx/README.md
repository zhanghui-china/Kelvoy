## 端口(黑客松节点,规则和共享机完全不同——只看这份,别套用共享机那张表)

组委会**只给每台节点做了两个公网端口映射**,其余端口哪怕在监听也从公网访问不到:

| 用途 | 节点内网端口 | 公网端口 |
| --- | --- | --- |
| SSH | 22 | 6063 |
| 服务 A | 8888 | 8063 |
| 服务 B | 9000 | 9063 |

**这条直接影响部署方案**:`services/inference` 现在默认 `8100`、`apps/web` 默认 `3000`,这两个端口都不在 8888/9000 里——如果黑客松演示需要公网直接访问,得把对外服务改绑到 `8888` 或 `9000`(内网端口),或者用 `ssh -L` 做隧道,不能指望现在的默认端口在这台机器上直接对外可访问。服务必须显式绑 `0.0.0.0`,绑 `127.0.0.1` 的话端口映射穿不透。

节点内网还看到 8000/8188/80/631/9100/53/11000 有进程在监听(8188 大概率是组委会镜像预装的 ComfyUI,和共享机的端口习惯一致)——这些都不对公网开放,不用担心冲突,但节点内部要跑自己的服务时,挑端口时避开它们比较省事。

## 部署模式(参考 visionary,不是照搬)

visionary 用 systemd `--user` 服务 + `Linger=yes`,不需要 sudo——这个模式适合共享、无 root 权限的账号,Kelvoy 可以照搬。但 visionary 的人工运维通道是"入站"(后端绑 `0.0.0.0:8000`,人从 Tailscale 直接连进来),**这和 Kelvoy PRD v0.2 §9 的"worker 只出站连接"硬约束是两码事**——那条约束管的是生产流量(worker 拉队列),人工 SSH/运维访问走 Tailscale 入站不违反它。对外公网暴露如果需要,visionary 用的 Cloudflare Tunnel(DGX 主动建出站隧道)这部分可以直接抄。

容器编排(裸 Docker / systemd / 别的)、模型权重具体怎么管理,还没定,等 M0-4 选完模型再定。
