# M0 工作手册

M0 的目标只有一个：在写产品代码之前证明"方法能出片、有人肯付钱、Spark 跑得动"。三件事任一不成立，后面都不用做。本手册对应 PRD v0.2 §10 的 M0 行，把交付物拆成可以两个人分头做、做完对得上的格式。

工期 1 周，owner 按人定。

## 0. 交付清单

| # | 交付 | 格式 | 验收 |
| --- | --- | --- | --- |
| 1 | 首批目的地包 3 条（南长街 / 拈花湾 / 灵山大佛） | `spike/m0/destinations/<id>.json` + 参考图 | 通过 §1 检查表 |
| 2 | 同一角色手工出片 3 期 | 3 个 mp4 + 每期一张出片记录表 | 每期 24–30 镜、9:16、带 AI 标识 |
| 3 | 一致性评审 | `spike/m0/review/<episode>.csv` | 3 期全量打分，算出通过率 |
| 4 | 模型评测 | `spike/m0/eval/结论.md`（一页） | 表格齐全，含"Spark 跑不跑得动"结论 |
| 5 | 用户访谈 10 人 | `spike/m0/interviews/<日期>-<代号>.md` | ≥ 3 人愿意预付；有价格锚点 |
| 6 | 数字回填 | PR 改 PRD v0.2 §1/§7/§8 的占位数字 | 积分汇率 X、估价常量、GPU 分钟目标有初值 |

`spike/m0/` 不 lint 不测，图片和视频不进 git（放共享网盘或对象存储，JSON 里写路径）。M1 用 `import-destination` 把 JSON 迁进正式库。

## 1. 目的地包录入规范

一个景区一条记录，字段与 `packages/engine/src/schema/destination.ts` 一致。

### 1.1 JSON

```json
{
  "destination_id": "d_wuxi_lingshan",
  "version": 1,
  "name": "灵山大佛",
  "city": "无锡",
  "type": "scenic_area",
  "season_best": ["春", "秋"],
  "landmarks": [
    {
      "id": "l1",
      "name": "灵山大佛",
      "refs": ["dest/d_wuxi_lingshan/l1_01.jpg", "dest/d_wuxi_lingshan/l1_02.jpg", "dest/d_wuxi_lingshan/l1_03.jpg"],
      "best_time": "上午顺光",
      "must_keep": ["比例", "手印", "莲花座"]
    }
  ],
  "route": ["山门", "九龙灌浴", "登阶", "大佛", "梵宫"],
  "food": ["素斋", "无锡小笼"],
  "transport": "地铁 + 公交 / 自驾",
  "stay": "景区周边民宿"
}
```

- `destination_id`：`d_<城市拼音>_<景区拼音>`，全小写。
- `type` 只能是六个值之一：`mountain_summit` 名山登顶 / `city_night` 城市街区夜游 / `theme_town` 主题小镇 / `scenic_area` 大型景区 / `water_town` 古镇水乡 / `island` 海岛。首批：南长街 → `city_night`，拈花湾 → `theme_town`，灵山大佛 → `scenic_area`。
- `landmarks[].id`：`l1`、`l2`… 景区内唯一即可。
- `must_keep`：写"一眼能看出错"的特征，3 个以内。这是 FR-04 生成时的硬约束和质量红线的判据，不要写形容词。
- `route`：按实际游览顺序，5–8 个节点，脚本阶段按它排镜头。
- `food` / `transport` / `stay`：给脚本用的信息槽位，各 1–3 项，不要写成攻略。

### 1.2 参考图要求

| 项 | 要求 |
| --- | --- |
| 数量 | 每个地标 ≥ 3 张，3–10 张为宜；至少一张远景（整体轮廓）、一张中景（主体 + 环境）、一张细节（`must_keep` 的特征） |
| 来源 | 自己实拍，或有明确授权的图；网图不要，版权来源要能说清 |
| 内容 | 无可辨认的路人正脸、无可读招牌 / 菜单（有的话裁掉或换角度）、无水印 |
| 规格 | 长边 ≥ 2000 px，JPG，横竖都行；每张文件名 `<landmark_id>_<两位序号>.jpg` |
| 标注 | 拍摄时段写进 `best_time`；如果某张只在特定季节成立（樱花、雪），文件名后加 `_spring` 这类后缀并在 `season_best` 里体现 |

路径约定：`dest/<destination_id>/<landmark_id>_<NN>.jpg`。M0 期间实际文件放共享网盘同名目录。

### 1.3 检查表

- [ ] `type` 是六值之一
- [ ] 每个地标 ≥ 3 张图，含远 / 中 / 细节
- [ ] 每个地标有 `must_keep`
- [ ] `route` 顺序与实地一致
- [ ] 图片无路人正脸、无可读文字
- [ ] 版权来源能说清

## 2. 手工出片

用同一个角色做 3 期，照参考片的方法、按 PRD §4 六阶段手工跑，工具不限（ComfyUI、各家 API 网页、剪辑软件都行），但**每一步都要记录**，因为这三期同时是评审集和成本基线。

### 2.1 角色

- 一份文字描述（年龄 / 性别 / 发型 / 体态 / 表情）+ 3–7 张参考图（正 / 侧 / 全身 / 细节）+ 默认穿搭。
- 三期用同一份描述和同一组参考图；穿搭可以换，换了要记在期记录里。
- 参考图来源自己定（上传真人照片允许，责任自负，见 PRD §3），但 M0 建议至少测一版生成图角色，方便对比一致性差异。

### 2.2 每镜记录表

每期一张，30 行，列如下（CSV 或表格都行）：

| 列 | 说明 |
| --- | --- |
| `no` | 镜号 1–30 |
| `scene` / `beat` / `size` / `camera` / `landmark` | 脚本字段，与 PRD §6 一致 |
| `kf_provider` / `kf_model` / `kf_seed` / `kf_attempts` / `kf_seconds` / `kf_cost` | 关键帧：用了什么、试了几次、耗时、费用 |
| `clip_provider` / `clip_model` / `clip_seed` / `clip_attempts` / `clip_seconds` / `clip_cost` | 视频：同上 |
| `trim_start_s` | 选的 1 秒起点 |
| `kept` | 进成片了吗（删镜写 no） |
| `note` | 为什么重生成、哪里崩了 |

`*_seconds` 是模型实际跑的秒数，不含排队和人工。M1 的估价常量和积分汇率就从这三张表算。

### 2.3 每期记录

- 模式（逐镜 / 网格）、季节 / 时段、穿搭
- 三个审核点各花了多少分钟（人工时间，单独记）
- 最终镜数、成片时长
- 配乐来源与授权

## 3. 一致性评审

### 3.1 评审集

3 期全量，每镜取"选定关键帧 + 成片里那 1 秒"作为一个样本。删掉的镜不评。样本数 ≈ 72–90。

### 3.2 打分

每个样本对照角色参考图，四项各打 pass / fail：

| 项 | 对照 | fail 的例子 |
| --- | --- | --- |
| 脸型 | 参考图 | 脸变宽 / 变长、下颌线明显不同、换了一张脸 |
| 发型 | 参考图 | 长度 / 分缝 / 颜色变了 |
| 体态 | 参考图 | 胖瘦 / 身高比例 / 肩宽明显不同 |
| 服装 | **本期**的穿搭描述 | 颜色 / 款式 / 配饰漏了或变了 |

四项全 pass 该样本才算通过。通过率 = 通过样本 / 总样本，目标 ≥ 90%，**按期分别算，也算总的**。

地标镜头另加一项"地标保真"：对照 `must_keep` 逐条 pass / fail，任一 fail 即该镜地标不合格。单独算合格率，这是 §4 模型评测的输入。

### 3.3 流程

- 两人各自独立打完再合，不一致的样本一起看一遍定结论，记下分歧原因。
- 评审表列：`episode, no, face, hair, body, outfit, landmark_ok, reviewer, note`。
- 打分时只看"是不是同一个人 / 同一件衣服"，不评画质、构图——那是模型评测的事。

## 4. 模型评测

在 Spark 上跑，2 个开源图像 + 2 个开源视频 + 1 个国内 API 做对照。基准图固定用灵山大佛、迎客松、清名桥各一张。

每个候选记：

| 列 | 说明 |
| --- | --- |
| `model` / `version` | |
| `runs_on_spark` | 能不能起、显存够不够；跑不动直接写原因，后面列留空 |
| `sec_per_shot` | 单镜生成秒数（图像一张 / 视频一段 3–5 s） |
| `fail_rate` | 10 次里崩几次 |
| `drift` | 用同一角色跑 10 镜，按 §3 打分的通过率 |
| `landmark_fidelity` | 三张基准图各跑 3 次，`must_keep` 合格率 |
| `cost` | 开源写 Spark 分钟数，API 写元 |

结论页只回答四个问题：图像环节留本地还是走 API；视频环节留本地还是走 API；单期 GPU 分钟目标定多少；整期全走 API 大概多少钱（对照 §8 的 ¥20 上限）。

## 5. 用户访谈

10 人：景区 / 文旅账号 / 本地代运营各至少 2。每次 30 分钟，记录用他们的原话，不要总结成我们想听的。

提纲：

1. 现在旅游内容怎么做的：谁拍、多久一条、一条成本多少。
2. 最头疼的是什么（人手 / 成本 / 人设不稳定 / 去不了那么多地方）。
3. 看 3 期样片：第一反应；能不能看出是 AI；能不能看出是哪个景区；虚拟角色接受吗。
4. "同一个角色每周去 3–5 个地方各出一条"这件事对你有用吗，用在哪。
5. 愿意为一期付多少；月订阅 / 按期 / 年度采购哪种顺手。
6. 什么情况下绝对不会用（AI 标识、平台风险、领导不认…）。
7. 现在愿意预付吗；愿意的话多少、要什么保证。

记录文件末尾固定三行：`预付意愿: 是/否/金额`、`价格锚点: `、`一句话结论: `。

## 6. M0 结束时回填

把下面几个数从 §2–§4 的记录里算出来，开一个 PR 改 PRD v0.2：

- §1 / §8：单期 GPU 分钟目标；整期全走 API 的实际费用 vs ¥20
- §8 / FR-09：积分汇率 X（1 积分 = 多少 GPU 分钟等价）；估价常量（候选数、单位成本、返工系数 1.5 是否合适）
- §7：每个环节留本地还是走 API；Spark 跑不动的候选划掉
- §11：解决掉的开放问题打勾，新冒出来的加上
