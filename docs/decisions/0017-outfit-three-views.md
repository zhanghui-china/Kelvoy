# ADR-0017 穿搭三视图：据一张全身照生成正 / 侧 / 背，拼成一张设定图作人物参考

状态：已采纳（2026-10-13），本 ADR 只落数据模型与文档；生成、上传与消费链路由后续任务实现

## 背景

ADR-0015 让每套穿搭自带 1–3 张图并替代 `refs[0]`，ADR-0016 的局限段指出：只有半身或单一角度的参考图时，全身镜头的下半身、背面是模型编的，同一期内不一致（阿澄三镜裤子分别是格子裤、米色裤、牛仔裤）。要求用户补齐多角度照片门槛太高。

T0 实验（`spike/three-views/README.md`，GX10，2026-10-13）：1 张全身照 → 正 / 侧 / 背三张（提示词 V1），横拼成一张设定图作关键帧的人物参考，12/12 单人、服装与背包保留、地标清晰，一致性与现状相当。

## 决定

1. **产品语义**：每个穿搭 = 一套三视图。用户只提供 1 张全身照（`source`），系统生成 front / side / back 三张并拼成 `sheet`。角色基础图的 `refs[0]` 视作「默认穿搭」的 source，三视图记在 Persona 自身。
2. **方案 A**：三视图横拼成一张设定图，作**单一**人物参考，参考图张数不变（仍是 `[人物, 地标]`）。创建作品选定穿搭后，关键帧只用该穿搭的 `views.sheet`。方案 B（四参考图）不做，理由见 spike README。
3. **提示词与拼图规格**：视角生成提示词 V1、关键帧侧「图1 = 设定图」前缀、拼图规格（正|侧|背 横拼、等高、JPEG q92）逐字沿用 `spike/three-views/README.md`，不在本 ADR 复制，避免两处漂移。
4. **数据模型**（与 PRD §6 同步；全部可缺省）：`PersonaOutfit` 增 `source?`、`views?`、`views_status?`、`views_gen?`，`Persona` 增同形的 `views?` / `views_status?` / `views_gen?`。`views` 仅在 `views_status === "ready"` 时存在，`views_gen`（provider/model/version/seed）同。`validatePersona` 校验这些一致性。
5. **refs 约束的最小改动**：`OUTFIT_REFS_MIN` 保持 1，不改常量（store 与上传路由的旧路径仍用它）。文档层校验改为：`source` 与 `refs` 二选一必有其一——有 `source` 时 `refs` 可为 0–3 张，没有 `source` 时仍要求 1–3 张。`views` 存在必须有 `source`。理由：三视图穿搭只上传一张图，强求 `refs` 非空会逼出一张重复的冗余 key；去掉下限又会放过两者皆空的废穿搭。
6. **零迁移**：老穿搭、老角色没有 `views` 字段，视为 `none`。消费端用 `outfitSheetKey(persona, outfitId)`（engine，纯函数）取 sheet：未 ready 返回 null，调用方兜底到原有的 `refs[0]` 逻辑。`keyframe-references` 的消费逻辑在本 ADR 范围外，由后续任务切换。
7. 三视图文件与 `refs` 一样只追加：旧版本引用的文件不删除（PRD §3）。重新生成写新 key，不覆盖。

## 修订 ADR-0015

- 「不做按文字生成穿搭图」：仍不做按**文字**生成；现在允许**据用户上传的这张照片**生成同一人物的其他角度。不凭空生成与上传图无关的人物。
- 「同时给多张图会画成两个人」：该结论针对多张不同图同时输入。现在不同时给多张——三个视角拼成**一张**设定图，实验 12/12 单人，前提改为「只给一张拼合设定图」。「选中穿搭替代 `refs[0]`」不变。

## 更新 ADR-0016 局限

「只有半身参考图时全身镜头的下半身是模型编的」：用户上传全身照时由三视图缓解（背面与侧面有依据）；上传半身照时三视图里的下半身仍是模型编的，该局限保留。「按朝向自动选图」仍不做：设定图自带三视角，是否足以压住朝向问题待端到端复核。

## 合规口径

三视图是据用户上传照片生成的视角图，肖像权与合规责任沿用 PRD §3，由用户承担；系统不凭空生成与上传图无关的人物。生成记录（provider/model/version/seed）随文档保存，可追溯。成片仍带可见 AI 标识。

## 未验证项与移除条件

T0 只覆盖 AI 生成的写实图，下列项未验证，验证前不得对外宣称支持：

- 真人实拍照（会不会漂脸、背景杂乱时三视图是否稳定）；
- 关键帧的正面、背身、近景、半身镜头（只测了侧身构图）；设定图在 9:16 工作流里缩放对脸部细节的影响；
- 直出视频（H3 Ref2VA）用设定图作人物参考；当前直出视频暂强制照片兜底（`personaReference(..., { photoOnly: true })`），移除条件：GX10 回放校验设定图作 Picture 1 后；
- 脸部一致性只是肉眼看，样本为 2 角色、12 张关键帧。

移除条件：在 GX10 用真人照与真实 `kf_prompt` 端到端复核（PRD 一致性目标 ≥ 90%）后，在本 ADR 追加结论；若直出视频或近景不达标，按镜头类型回退，不改数据模型。

## 回退办法

字段全部可缺省且只追加：停用三视图只需让生成链路不再产出 `views`（或把 `views_status` 置 `none`），`outfitSheetKey` 返回 null，消费端自动回到 `refs[0]` 的 ADR-0015 行为。无需数据迁移；已生成的三视图文件保留，不会影响旧作品。

## 拼图依赖

worker 用 sharp 拼图，不用 ffmpeg。理由：ADR-0004 规定 `compose` 是唯一碰 ffmpeg 的地方、且只在 worker 上跑，拼图若走 ffmpeg 会让这条边界失效；sharp 已是 `apps/web` 的依赖（版本一致，0.35.5），worker 新增它不引入新的库选型。`composeSheet` 的签名与拼图规格不变，只替换实现。

## 已知限制：三视图 job 与分镜任务共用 worker 循环

`apps/worker/src/queue/consumer.ts` 只在没有阶段任务时才领取三视图 job，单个 job 最长 20 分钟（`VIEWS_JOB_TIMEOUT_MS`）。分镜队列持续不空时三视图会饿死，三视图执行期间新提交的分镜任务最多等待 20 分钟。上线初期用户量小，暂接受；若出现排队投诉，给三视图单独并发槽（移除条件：三视图排队时长在线上超过一个阶段任务的耗时）。

## 已知限制：重新生成期间不可用于建作品

对已 ready 的穿搭重新生成时，目标先置为 `pending` 并暂时移除旧 views。此时以该穿搭建作品会被拒绝（`409 outfit_not_ready`），不会静默退回 `refs[0]`。
