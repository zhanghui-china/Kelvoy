# M0-4 Spark 模型评测：技术摸底（图像 + 视频）

对应 issue #4「M0-4 Spark 模型评测：2 图像 + 2 视频 + 1 国内 API」。

## 这份文档回答什么、不回答什么

**只回答**：这几个候选在 Spark（黑客松分配节点 spark-63）上跑不跑得动、多快、参考图条件生成对地标保真有没有实际帮助——纯技术可行性摸底，**不是可以直接拍板的最终结论**。

**局限（在结论之前必须先看这几条）**：
- 地标参考图是维基百科公开图库图（灵山大佛、迎客松、清名桥各一张），**不是 #1 目的地包的实拍图**。#1 还没做，真正的地标保真度评审要等实拍图出来后重测。
- 没有做跨镜/跨期一致性、漂移率测试——那是 #3 一致性评审的范围，需要真实角色资产和多镜序列，这次只测了单张图/单段视频。
- 国内 API 候选（StepFun）不在这份文档里——团队决定 StepFun 只用于 LLM/脚本生成环节，图像和视频全走本地模型，StepFun 的评测由另一项工作单独处理。
- 视频候选没有测 9:16 竖版分辨率（Kelvoy 目标输出格式），下面的视频结果用的是模型训练默认的 1344×768 横版——这是为了先验证"能不能跑通"，不是最终交付分辨率的验证。

## 环境

黑客松分配节点 `spark-63`（内部主机名 `spark-c327`，见 `infra/dgx/README.md`），GPU：NVIDIA GB10，统一内存 130GB。模型文件由队友 wuzi/zhanghui 预先下载在节点上，ComfyUI 常驻 `127.0.0.1:8188`。测试通过 ComfyUI 的 HTTP `/prompt` API 提交，没有复用队友手工搭的网页 workflow（没保存下来），根据 ComfyUI 官方模板 + 节点自带的 example workflow 重新拼的 API 版本。

## 逐项细节

### Qwen-Image 2.1（对照组，不给参考图）
`qwen_image_2.1_int8_convrot.safetensors` + `qwen3vl_8b_bf16.safetensors` + `qwen_image_2.1_vae_bf16.safetensors`，25 步 euler/simple，1024×1024，prompt 里直接写地标中文名。三次全部成功，34–42 秒。生成结果里灵山大佛的姿势、法衣、莲花座细节都对，说明这类全国知名地标模型"认识"，仅靠文字描述就有不错的保真度——**这削弱了"必须靠参考图"这条论证对超知名地标的说服力，但 Kelvoy 首批目的地里南长街、拈花湾这类没有灵山大佛那么高辨识度，参考图条件生成的价值大概率在这些目的地上更明显**，这次没测这一层对比。

### Qwen-Image-Edit 2511（参考图条件生成，FR-04 硬约束的候选）
`qwen_image_edit_2511_int8_convrot.safetensors` + `qwen_2.5_vl_7b_fp8_scaled.safetensors` + `qwen_image_vae.safetensors`，参考图经 VAE 编码后以 denoise=0.85、cfg=2.5、20 步跑图生图。三次全部成功但耗时差异巨大：
- 灵山大佛（1110×1468 参考图）：114.8 秒
- 清名桥（800×552 参考图）：约 49 秒
- 迎客松（**3648×2736**，团队原图未压缩）：约 784 秒（13 分钟）

**工程发现**：参考图分辨率直接决定耗时，13 倍的分辨率差距对应 13 倍的耗时差距——生产环境喂给这个模型前必须先把参考图统一下采样到合理尺寸，不能让用户上传的原图直接进模型。

**质量发现**：三次生成结果里地标本身的还原度都很高（清名桥那张连石碑上"大运河 清名桥"的字都清晰保留），但没有一次真正显示出 prompt 要求的"游客站在前景"——模型基本只是复刻原图加了色调滤镜。这说明这次的采样参数（denoise/cfg）偏保守，验证了"能保真"但没验证"能按指令改"，这是本次评测最大的技术缺口，需要后续用更高 denoise 或换一种参考图注入方式（比如 ControlNet 式结构参考而非直接图生图起点）重测。

样片：`~/ComfyUI/output/KelvoyEval/qwen_edit_0000{1,2,3}_.png`（远端节点），本地留档在 `/private/tmp/.../scratchpad/kelvoy-eval/outputs/`（会话临时目录，非仓库路径）。

### MiniMax H3（首帧生视频）
`minimax_h3_fl2va_pruned_int8_convrot.safetensors` + `qwen3vl_32b_minimax_h3_int8_convrot.safetensors` + `minimax_h3_video_vae_int8_convrot.safetensors`/`minimax_h3_audio_vae_fp32.safetensors`，用 `MiniMaxH3ImageToVideo` 把地标参考图设为 first_frame，`MiniMaxH3DualClockSamplerT8` 8 步采样（`dual_clock_euler`），1344×768，124 帧（~5s）。两次全部成功：
- 灵山大佛：603.1 秒
- 清名桥：346.5 秒

**注意**：这次**没有用团队昨天验证过的 Turbo LoRA 加速**——示例 workflow 引用的 lora 文件名（`minimax_h3_turbo_4步加速ema_comfyui.safetensors`）在节点上找不到完全对应的文件，为了保证这次摸底先把"能不能跑通"这条主线跑稳，没有替换成近似版本去赌兼容性。所以这次的耗时（347–603 秒）比团队昨天用 Turbo LoRA 跑出来的（213–300 秒）慢，**不代表 MiniMax H3 的产品化速度上限**——后续要接上正确版本的 4-step turbo lora（节点上有 `minimax_h3_fl2v_turbo_4step_v1.2_768p_comfyui_bf16.safetensors` 等几个候选版本）重测才有意义。

首帧是参考图本身（锚定机制决定的，不是生成的），所以首帧地标保真度是 100%；完整视频里地标有没有随镜头运动漂移、变形，需要真人看一遍 mp4，样片在远端节点：`~/ComfyUI/output/KelvoyEval/minimax_h3_0000{1,2}.mp4`，本地留了首帧截图在 scratchpad。**这次没测 9:16 竖版**，只用了模型训练默认的横版分辨率验证跑通与否。

### LTX-Video 2.5（完全没跑）
本地只下载了 transformer 主干权重（`ltx-2.5-22b-distilled-transformer-comfy-int8-convrot.safetensors`，约 20GB）。官方 ComfyUI-LTXVideo 节点包自带的示例 workflow（`LTX-2.5_T2V_I2V_Single_Stage_Distilled.json`）明确要求额外三个文件：专用视频 VAE（`ltx-2.5-video-vae-*.safetensors`）、专用音频 VAE（`ltx-2.5-audio-vae-bf16.safetensors`）、专用文本编码器（`gemma4-12b-with-proj-ltx-2.5-bf16.safetensors`）——这三个节点上完全没有。

这不是"显存不够"或"报错崩溃"，是**环境不完整**：要跑通大概还需要再下载 30GB+ 的模型文件。这次摸底为了控制时间没有额外下载，留给后续需要正式测 LTX-Video 时再补。

## 回答 issue #4 的四个验收问题（初步，非最终）

- **图像留本地还是走 API**：本地明显可行（Spark 跑得动，30-50 秒级），但这次没测国内图像 API 做对照，无法下结论哪个更划算/更快；本地至少证明了"跑得动"这条门槛。
- **视频留本地还是走 API**：本地可行但慢（347–603 秒一段 5 秒视频，且没用加速 LoRA），PRD 风险表原本就预判"视频环节大概率长期走 API"——这次的本地耗时数据支持这个预判方向，但需要接上 Turbo LoRA 重测才能给出更接近生产的数字。
- **单期 GPU 分钟目标**：这次没有覆盖到"一期 24-30 镜全部跑一遍"的规模，只做了单镜/单张验证，还不能回填这个数字。
- **整期全走 API 多少钱 vs ¥20**：本地测试不产生这个数字，需要国内 API 候选（视频）的实际报价对照，这次没测。

**这四条都还没有到能定论的地步**——M0-4 要给出完整回答，还需要：(1) 接上 Turbo LoRA 重测 MiniMax H3 的真实速度；(2) 补齐 LTX-Video 缺的模型文件再测一次；(3) 用 #1 的实拍参考图重做一遍图像/视频的保真度评审；(4) 找一个国内视频生成 API 做实际报价对照（issue 原文要求"1 国内 API"，团队决定 StepFun 只做 LLM，图像/视频国内 API 对照目前是空的，需要另外决定测哪家或者明确"不测，全走本地+开源"这个结论）。
