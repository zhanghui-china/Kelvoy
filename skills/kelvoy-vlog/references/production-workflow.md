# 生产流程

本文用于一次生产或返工。请求字段和部署差异见 [API 参考](kelvoy-api.md)。

## 需求与准备

先确认用户提供的服务地址和会话。通过只读接口读取角色、目的地、模板；名称不是 ID。同名对象展示 ID 与必要描述后让用户选择。

角色应有可用参考图；目标版本要求自定义角色三视图时，必须处于已确认状态。官方角色沿用已有参考图。不可自动确认待审或过期批次；引导用户到 `/personas/<persona_id>/edit`。

目的地按景区记录选择，地标引用必须存在于其 `landmarks`，地标镜头需要实景参考图。模板按用户要求选；用户未指定时展示与目的地类型对应的候选，不擅自选择多个匹配中的一项。未入库素材留给现有页面或维护者处理。

提交前简述角色、目的地、模板、风格与穿搭；只追问未确定项。默认 `mode=per_shot`。服务设置季节、候选数、版本与输出参数，不在客户端捏造派生字段。

## 状态与观察

正常流程：

```text
draft → scripting → script_review → assets → keyframing → kf_review
      → clipping → clip_review → composing → done
```

生成状态可能进入 `failed`，也可能在期仍可审核时出现单镜 `failed`。读取每镜状态以及可用的 `failure_reason`，不能只看整期状态。

- 每轮观察最多 60 秒，约 5 秒查询一次。观察结束仍未完成时反馈阶段、待处理镜头和作品 ID，不把等待超时当任务失败。
- 不从 Agent 另起生成循环；服务负责后续阶段、自动重试与队列调度。
- 转入审核态即停止自动推进，呈现内容并取得本次审核决定。
- 用户在 Web 审片时可提示其完成后回复；恢复时重新读作品，认可服务中已有选择，不重复写入。

`pacing_version=2` 新期通常 5–10 镜、目标每镜 3–6 秒、至少 2 镜地标；缺失该字段的旧期使用 24–30 镜、至少 5 镜地标与旧剪辑规则。两类都要求地标引用有效、同景别不连续超过 2 镜。实际校验以对应服务版本为准，不能为通过校验自动迁移旧期。

## 审核 1：脚本

展示镜号、场景、动作、景别、镜头运动、地标名称及目标时长。检查一镜一个主要动作，地标来自资料库；把风格或连贯性建议与用户决定区分开。

允许改 `beat/size/camera/landmark/kf_prompt/motion_prompt`，删除或重排已有镜头。不新增镜头，不直接改 `no/scene/duration_s`。重排提交全部现有镜号的排列，服务重编号；删除、重排后重新读取镜号再处理后续决定。

展示服务返回的规则错误，不用绕过校验的写入方式。用户明确通过当前脚本后调用 `/continue`，不能直接 PATCH 期状态代替审核推进。

## 审核 2：关键帧

按原始候选顺序，给每镜标明“候选 1、2…”并映射到实际文件 key；展示地标实景参考及角色参考。候选序号仅用于展示，提交的是文件 key。不得编造自动质量分数或把候选排序当人工选择。

- `kf_ready` 选择时同时写 `kf_selected` 与 `status=kf_selected`。
- 已处于 `kf_selected` 时换图仅写 `kf_selected`；同状态重复转移可能被拒绝。
- 已进入视频或已审核的镜头，不能直接换图指针保留旧片段；使用关键帧返工流程。
- 候选必须属于该镜当前 `candidates`。重生成完成后旧选择失效，需重新展示候选并取得选择。
- 提交用户选择时使用最新期级 `row_version`，多镜决定串行提交。

推进前，每个需视频生成的镜头都必须为 `kf_selected` 且所选 key 属于 `candidates`。返工中保留的镜头可为 `approved` 且有 `clip`。部署基线还要求至少一镜需要生成视频；所有镜已 approved 却停在 kf_review 时交维护者核对，不能伪造选择状态。存在失败、生成中、未选择或旧候选指针时不能继续。选择完成和“继续生成视频”决定可在同一用户回复中给出。

## 审核 3：片段

提供每镜片段播放器或审片链接、目标时长、已保存的 `trim_start_s`。实际素材时长由播放器或 ffprobe 检查，未知时不猜起点范围。起点应非负，且可容纳对应切段。

请用户检查人物／穿搭一致、手部正常、地标正确、动作符合物理、无幻觉可读文字。这些确认不是 API 中的五个布尔字段，不伪造请求字段。

用户明确通过某镜后保存其决定，`clip_ready → approved`；已 approved 的镜不用重复写同一状态。修改切点是独立操作，可与审核在同一个 PATCH 中保存，但仍需用户决定。重生成的片段重新审核。

推进合成前所有镜头必须为 `approved` 且 `clip` 非空。没有媒体查看能力时由用户在 `/episodes/<episode_id>` 完成审核，不代替其批准。

## 返工与重新合成

区分两种镜头操作：

| 当前情况 | 操作 |
| --- | --- |
| 已有候选／片段需要改做 | 保存用户要求的 prompt，随后 `/regen`，明确 `regen_stage` |
| 镜头 `failed` 且自动重试耗尽 | 支持的实例用 `/retry`；需要用户决定，阶段不能臆测 |
| 仍在生成 | 只观察；不叠加任务 |
| 成片需重剪或合成失败 | `/recompose`，保留已审核镜头 |

prompt 写入失败就停止，不用旧 prompt 开新任务。已 `kf_selected` 镜头请求关键帧返工时，部署基线的 `/regen` 可能拒绝该源状态；返回 `illegal_transition` 后保持选择并说明限制，不能伪造状态来解锁。参考 [API 状态限制](kelvoy-api.md#返工与合成)。

局部返工后读取作品，核对其他镜头的候选、已选图和片段未变。被替换的片段与选图重新过对应审核点。重新合成只提交合成任务，不使用单镜生成接口。

缺配乐时展示可行选择；用户明确选无配乐、部署版本支持 `music.enabled=false` 且完整 music 对象能通过校验时，先保存选择，再重合成。原 music.file 为空而目标校验器不接受时报告限制，不捏造文件名。素材不足由服务报告差额，不能偷偷缩短时长。

## 中断与交付

一次恢复记录包含服务地址、作品 ID、最后观察状态及待执行决定，不存密码或 cookie。再次工作先 GET 作品。

写请求结果未知时：

1. 查询作品与镜头状态，看预期变化是否已生效。
2. 能证明生效则继续观察；冲突变化则重新呈现给用户。
3. 不能确定则暂停该操作并交维护者核对队列；不能凭“状态没变化”认定任务没入队。
4. 建期没有拿到 ID 时读作品列表，按提交时间、角色、目的地、模板和 brief 核对；多个匹配或仍不明时不再建期。

`done` 是交付前提；成片 key 来自当前版本的明确文件约定，不猜服务器绝对路径。文件 GET 成功、内容确为视频才报告可访问。媒体参数经实际文件探测才写“实测”，仅来自 `render` 时写“配置目标”。AI 水印靠画面检查，元数据可由 ffprobe 核对，`ai_label=true` 本身只是配置证据。

给出需登录的下载链接与审片链接；仅用户要求分享才调用分享接口。模型成本读取 `shots[].model`，没有调用记录或估价为占位时如实说明。
